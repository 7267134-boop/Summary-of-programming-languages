סיכום למבחן: מערכות טיפוסים

פרק 7 - שפות CHECKED ו-INFERRED

1. למה טיפוסים? (Static vs Dynamic Typing)

עד כה בנינו מפרשים (כמו PROC) שתפסו שגיאות טיפוס רק בזמן ריצה. המטרה בפרק זה היא לתפוס שגיאות בשלב התרגום (Compile-time) לפני שהתוכנית בכלל רצה.

ההבדל בין הסביבות

  • סביבת ריצה (Env): פועלת ב-value-of. ממפה מזהה לערך (למשל: x = num-val(5)).
  • סביבת טיפוסים (Tenv): פועלת במנוע ההסקה הסטטי. ממפה מזהה לטיפוס (למשל: x = int-type).

2. שפת CHECKED (טיפוסים מפורשים)

שפה הדורשת מהמתכנת להצהיר במפורש על כל טיפוס (כמו proc (x : int)). מתבצע Zero-Cost Abstraction: אחרי שהקוד עובר אימות טיפוסים, מפרש הריצה מהיר יותר כי הוא מניח שהקוד בטוח לחלוטין ואין בו בדיקות טיפוסים כלל.

מנוע הבדיקה (checker.scm)

הפונקציה type-of סורקת את ה-AST ומחשבת טיפוסים ע"י התאמת חוקים והשוואות באמצעות הפונקציה check-equal-type!.

הצורך בהצהרות ברקורסיה

ב-letrec חובה להצהיר מראש על טיפוס ההחזרה. הסיבה: המפרש חייב לרשום את הפונקציה ב-Tenv לפני שהוא מנתח את הגוף שלה, כדי שהקריאה הרקורסיבית בגוף תהיה חוקית.

3. שפת INFERRED (הסקה אוטומטית)

שפה חכמה בה המתכנת משתמש ב-? במקום להכריז על טיפוס. המהדר מסיק את הטיפוסים כמו בפתרון מערכת משוואות מתמטיות.

ארכיטקטורת המפרש:

  • משתני טיפוס (Gensym): כל סימן ? (או כל תת-ביטוי) מקבל משתנה זמני טרי (כמו $t_1, t_2$).
  • הפרדת רשויות: ה-inferrer.scm מכיר תחביר (AST) ואוסף משוואות. ה-unifier.scm חי בעולם של אלגברה נטו ופותר משוואות ללא היכרות עם התחביר.
  • השחלת מצב (State Threading): כדי להעביר את הידע שנצבר, המפרש לא מחזיר רק טיפוס, אלא an-answer: אובייקט המכיל את הטיפוס ואת מילון ההצבות (Substitutions) המעודכן שעובר לניתוח של הביטוי הבא.

4. שלב א': גזירת חוקים ואיסוף משוואות (Constraints)

ה-Inferrer סורק את העץ מלמטה למעלה (Bottom-Up) ומשליך אילוצים:

הביטוי (Expression) משוואה מחייבת משמעות ודגשים
-(E1, E2) t1=int, t2=int, t_res=int אופרטור מתמטי דורש ומחזיר מספרים.
if E1 then E2 else E3 t1=bool, t2=t3, t_res=t2 התנאי בוליאני, ושני הענפים חייבים להחזיר אותו טיפוס.
proc (x) Body t_res = t_x → t_body בונה טיפוס מורכב (Type Constructor) מסוג פונקציה.
(Rator Rand) t_rator = t_rand → t_res החוק החשוב ביותר! הטיפוס של הפונקציה מאולץ ע"י הקלט שהיא מקבלת והפלט שהיא מחזירה.
let x = E1 in E2 t_res = t_E2 קשירת סביבה: ה-let עצמו לא מייצר משוואה עבור x, אלא מכניס את t_E1 ל-Tenv כדי ש-E2 יכיר אותו.

5. שלב ב': אלגוריתם ה-Unification (אלימינציה)

ה-Unifier מריץ תהליך איטרטיבי על כל משוואה (למשל $L = R$) בעזרת 4 כללים טוריים (Just-In-Time):

  1. זהות (Identity): אם $L$ ו-$R$ הם בדיוק אותו טיפוס (למשל $int = int$), מתעלמים מהמשוואה וממשיכים.
  2. גילוי משתנה (Substitution): אם צד אחד הוא משתנה זמני ($t$) והצד השני הוא טיפוס כלשהו:
    ← חובה לבצע Occurs Check! (ראו סעיף הבא)
    אם הבדיקה עברה, מוסיפים לטבלת ההצבות, ומחליפים את ה-$t$ הזה בכל משוואה עתידית שננסה לפתור.
  3. פירוק פונקציות (Decomposition): אם יש משוואת חצים (למשל $t_1 \rightarrow int = bool \rightarrow t_2$), מפרקים אותה לשתי משוואות פשוטות יותר:
    $t_1 = bool$ (שמאל מול שמאל)
    $int = t_2$ (ימין מול ימין).
    הערה: הפירוק קורה ברצף טורי, קודם ארגומנטים ואז תוצאות.
  4. שגיאת טיפוס (Failure): אם הגענו לסתירה מהותית ($int = bool$), האלגוריתם נכשל וזורק שגיאת איחוד (Unification Failure).

6. מקרי קצה ותובנות חשובות

⚠️ למה חייבים Occurs Check?

בדוגמה של פונקציה שמפעילה את עצמה (x x), נוצרת המשוואה: $t_x = t_x \rightarrow t_{res}$.
אם האלגוריתם היה פשוט מציב את הימין לתוך השמאל ללא בדיקה, היינו מקבלים התפוצצות בזיכרון (Infinite Loop / Stack Overflow):

1. (t_x → t_res) → t_res
2. ((t_x → t_res) → t_res) → t_res ...
[CRASH]

מטרת ה-Occurs Check היא לוודא שהמשתנה ($t_x$) לא מופיע בתוך המבנה שמציבים בו. אם הוא שם → זורקים שגיאה מיד!

🔒 אין פולימורפיזם אמיתי (Monomorphic Lock-in)

בשפת INFERRED של פרק 7, גם אם פונקציה כמו ה-Identity Function proc(x:?) x מסיקה משתנה טיפוס חופשי ($t_x \rightarrow t_x$), ברגע שנפעיל אותה בתוכנית על 5, המשתנה $t_x$ ננעל על int לכל אורך התוכנית!
כל ניסיון להפעיל את אותה הפונקציה לאחר מכן על true יזרוק שגיאת Type Clash. המערכת היא מונומורפית (Monomorphic Inference).
